## 1. 按键极性判反：空闲被当成“一直按住”

**触发条件**
按键电路是“引脚经电阻上拉到 VCC，按下接地”（低有效），而代码按“高有效”处理，
在顶层对按键输入做了取反。

**现象**（四个同时出现，这是关键特征）
- 上电不按任何键，频率一路降到下限（`F=00100`）；
- 相位值持续自行增加（每 50 ms 加一次），两路相位差一直在变；
- 加减方向自动变成“减”（`D=-`）；
- **真按住某个键时，该键对应的功能反而“没反应”**。

**为什么难发现**
单看每个现象，都能找到合理的外部解释：
频率往低走像是“引脚悬空乱跳”，相位在变像是“相位字被噪声改写”，
方向变减像是“抖动”。四个现象各自解释，就会去修四个地方。

真正的线索是第四个现象：**“按下反而没反应”说明极性整体反了**，
不是某一路的问题。

**定位步骤**
1. 不要推测极性。把四路按键的**原始电平**（不取反、不消抖）加进状态报文，
   例如 `K=1111`。
2. 什么都不按，记下读数。
3. 依次按住每个键 2 秒，各记一行。
4. 对照：
   - 空闲 `1111`、按住第 n 个键时第 n 位变 0 → **低有效**，`PULLTYPE PULLUP`，模块内不取反
   - 空闲 `0000`、按住第 n 个键时第 n 位变 1 → **高有效**，`PULLTYPE PULLDOWN`，模块内取反
5. 若空闲不是全 0 也不是全 1 → 引脚有悬空或分压，先查硬件。

**修复**（本项目）
```diff
- PULLTYPE PULLDOWN          # XDC
+ PULLTYPE PULLUP

- .key_wave (~key_wave)      # 顶层例化
+ .key_wave (key_wave)
```

**留给下次的判据**
> 判断按键极性，**只看“空闲电平”和“按下时哪一位翻转”这两个读数**，
> 不要用“空闲读高就说明悬空”这种推断。把原始电平打印出来，
> 按一遍所有键，10 分钟能定，靠猜要一天。

## 2. 照抄社区引脚资料，把 VGA 当按键

**触发条件**
板卡是退役的通信设备板（如 EBAZ4205“矿板”），厂商没有公开的用户手册，
网上的引脚表来自个人逆向，且互相矛盾。

**现象**
按键接上去完全没反应。更迷惑的是：某些引脚能读到稳定的 0，看起来“像是被占用了”。

**为什么难发现**
读到的确实是稳定电平，不是悬空乱跳，所以第一反应是“这个脚被别的电路占了，换一个”。
于是换个脚再试，再失败，循环。本项目换了 6 个脚才意识到资料本身是错的。

实际情况：社区说的 `KEY1~5 = T19/P19/U20/U19/V20`，
在扩展板原理图里是 `VGA_G2 / VGA_B4 / VGA_HSYNC / VGA_G3 / VGA_VSYNC`——
读到的稳定 0 是视频信号的消隐电平，不是按键。

**定位步骤**
1. **先找原理图 PDF，找不到再谈社区资料**。退役板的原理图通常能在卖家资料包里找到。
2. 从 PDF 里检索网络标号。如果 PDF 是扫描图无法检索，用文本提取工具解析内容流
   （zlib 解压流 + 按 `Tm`/`Td` 坐标归行），本项目就是这么挖出正确引脚表的。
3. 拿“丝印名 + 网络名 + 引脚号”三者互相对照，**三者都对得上才算确认**。
4. 用第 1 条的实测法再验一遍。

**修复**（本项目）
真实按键为 S1~S4（丝印 KEY_1~KEY_4）→ **G19 / J19 / K19 / L16**，
经 220 Ω 上拉到 VCC_3V3，低有效。实测空闲 `1111`，逐键 `1110/1101/1011/0111`。

**留给下次的判据**
> 引脚表只有三个来源可信：**原理图、厂商手册、自己的实测**。
> 论坛帖子、博客、二手卖家口述都属于“线索”，不属于“依据”。
> 而且“读到稳定电平”恰恰可能是接错了的证据。

## 3. 用除法做参数换算，时序不收敛

**触发条件**
在 RTL 里写 `x = a * k / 1000` 这类含除法的参数换算，且除法结果直接驱动大位宽累加器。

**现象**
- 功能仿真完全正确；
- 综合能过；
- 实现后 WNS 为 **−1.877 ns**（50 MHz 约束），关键路径失败端点若干；
- 板上行为不可预测：多数时候能跑，温度或电压变化后偶发异常。

**为什么难发现**
仿真器不关心时序，仿真全过；综合不报错；只有在实现后的时序报告里才暴露。
而“偶发异常”很容易被归因为“接触不良”。

**定位步骤**
1. 看 `*_timing_summary_routed.rpt` 的 WNS。**每次实现后都看一眼**，不要等出问题才看。
2. 找关键路径：`report_timing -max_paths 5`，看 Source/Destination 是否跨了一个隐含的运算块。
3. 在源码里搜 `/` 和 `%`。**这两个符号在 FPFA 里几乎总是嫌疑对象**。

**修复**
把除法换成“乘常数 + 移位”：

```verilog
// 改前：freq_word = f * 85899 / 1000;   除法器，组合延迟过大
// 改后：÷1000 变成 ×(85.89934592) 的定点形式
wire [45:0] fw_prod = freq_hz[14:0] * 46'd1441151881;  // 85.89934592×2^24
freq_word <= fw_prod[45:24];                            // 右移 24 位
```

WNS：**−1.877 ns → +3.089 ns**，关键路径缩短 4.97 ns，定点误差 6×10⁻¹⁰，功能不变。

**留给下次的判据**
> 综合通过 ≠ 能跑。**WNS < 0 的比特流不要上板**，它的行为是“大部分时候对”，
> 这种 bug 比彻底不工作更难查。
> 另外：RTL 里出现 `/` 或 `%`，先想着换掉。

## 4. `.bat` / `.ps1` 的换行与编码

**触发条件**
用编辑器或脚本工具生成 Windows 批处理/ PowerShell 脚本，默认写出的是 **LF 换行** 和 **UTF-8 编码**。

**现象**（两种，都很迷惑）
- `.bat`：cmd 报 `'xxx' 不是内部或外部命令`，明明那一行写的是 `echo`。
  原因是 cmd 按 CRLF 解析，LF 文件会被当成一整行或错行拆分。
- `.ps1`：中文全变乱码，或者报语法错误。
  原因是 PowerShell 5.1 对**无 BOM 的 .ps1 按 ANSI（GBK）解析**，
  UTF-8 写的中文被当 GBK 解码。
- 更隐蔽的一种：`.bat` 里有中文注释，UTF-8 被按 GBK 解析后，
  `rem` 行被拆坏，跟着的几行一起失效。

**定位步骤**
1. 用十六进制看行尾：`0D 0A` 是 CRLF，只有 `0A` 是 LF。
2. 用十六进制看开头：`EF BB BF` 是 UTF-8 BOM。
3. 造一个最小复现：只写一行 `@echo off` + `echo hi`，若也报错，就是换行问题。

**修复**
- `.bat`：**GBK 编码 + CRLF**，且**不写中文注释**（全 ASCII 最稳）。
- `.ps1`：**GBK 编码 + CRLF**（PowerShell 5.1 可直接读），
  或者 **UTF-8 带 BOM + CRLF**（也能读）。
- 生成后用一行命令统一：
  ```bash
  python -c "b=open(p,'rb').read().replace(b'\r\n',b'\n').replace(b'\n',b'\r\n'); open(p,'wb').write(b)"
  ```

**留给下次的判据**
> Windows 脚本的三条铁律：**CRLF、编码显式指定、注释用英文**。
> 写完先运行一次空脚本，再往里填内容。

## 5. xvlog 2017.4 不支持 `-timescale`

**触发条件**
用 Vivado 自带仿真器（xsim）跑行为仿真，命令行里加 `-timescale 1ns/1ps`。

**现象**
```
ERROR: [Common 17-39] '-timescale' is not a valid option for 'xvlog'
```
或不加参数时，xelab 报 “design has no timescale”。

**为什么难发现**
新版 Vivado（2020+）的 xvlog 支持该选项，网上大部分教程也这么写。
2017.4 不支持，但错误信息只说不认识这个选项，不告诉你该怎么替代。

**修复**
把编译指令写进源码顶部（对综合无影响）：

```verilog
`timescale 1ns / 1ps
module cmd_parser (
```

只要设计里有**任何一个文件**声明了 timescale，xelab 就不再报错。

**留给下次的判据**
> 老版本工具链缺选项时，优先找“写进源码”的编译指令（`` `timescale `` `` `define ``），
> 而不是继续在命令行参数里试。

## 6. Vivado 下载时路径含中文

**触发条件**
在 Program Device 对话框里粘贴或拖拽比特流路径，路径中含中文目录名。

**现象**
```
Please use ASCII characters for file name or path.
```
下载对话框直接拒绝。

**定位步骤**
路径里逐级看有没有中文、空格、全角符号。

**修复**
- **手打**路径，不要拖拽（拖拽会把完整的含中文路径塞进去）。
- 或者先把 bit 复制到纯 ASCII 路径，例如 `D:/fpga/bit/7_key_dds.bit`。
- 根治：工程、桌面、用户名都别用中文。这一点在项目一开始就该定。

**留给下次的判据**
> 与 FPGA 工具链相关的一切路径**只用 ASCII**：工程目录、比特流、导出报告、脚本。
> 中文路径的问题不一定报错，有时是静默失败，更难查。

## 7. 串口被占用 / USB 选择性暂停

**触发条件**
- 上一个串口程序没关（窗口关了但进程还在），又打开同一个 COM 口；
- 或系统开启了 USB 选择性暂停，空闲一段时间后挂起 USB 设备。

**现象**
- 前者：`对端口"COM4"的访问被拒绝`；
- 后者：跑着跑着突然 `使用"0"个参数调用"DiscardInBuffer"时发生异常:"端口被关闭。"`，
  但设备管理器里 COM 口还在。

**为什么难发现**
第一种：用户以为窗口关了就是程序退了。
第二种：现象是“用着用着突然断”，像是代码 bug，实际是电源管理。

**定位步骤**
1. 查占用进程：
   ```powershell
   Get-Process | Where-Object { $_.ProcessName -match 'powershell|python|putty' } |
       Select-Object Id, ProcessName, StartTime
   ```
   按启动时间找出那个“以为已经关了”的进程，`Stop-Process -Id <id> -Force`。
2. 判断是不是电源管理：看是否“空闲一段时间后”才断。
   关闭 USB 选择性暂停：
   ```powershell
   powercfg /setacvalueindex SCHEME_CURRENT 2a737441-1930-4402-8d77-b2bebba308a3 48e6b7a6-50f5-4782-a5d4-53bb8f07e226 0
   powercfg /setactive SCHEME_CURRENT
   ```

**修复**
- 软件侧：每次发送前检查 `IsOpen`，异常则关闭重开并重发一次；
  端口号变化（COM4→COM5）时自动跟随。
- 一句话原则：**一个 COM 口同时只能被一个进程打开**，调试前先确认没有僵尸进程。

**留给下次的判据**
> 串口类问题先分清三类：**被占用（拒绝访问）/ 被挂起（用着断）/ 枚举变了（COM 号跳）**。
> 三类的修法完全不同，不要混在一起试。

## 8. 串口 RX 悬空捡噪声，凑出假命令

**触发条件**
UART 接收引脚没有接（或对端没上电），引脚浮空。

**现象**
没人动板子，参数自己变化。表现为“相位突然变成 0”“频率跳到某个值”。

**为什么难发现**
因为参数确实变了，会以为是按键抖动或状态机 bug。
而噪声字节本身不会显示在任何地方——除非你把收到的每个字节都打印出来。

**定位步骤**
1. 在串口接收模块后面接一个“收到什么就回显什么”的调试通路，看是否有字节进来。
2. 检查解析器的容错：**只有字母没有数字的命令是否会被执行**。
   例如 `P` + 回车，若被执行，相位就被拍成 0。

**修复**
给解析器加一条硬性校验：**命令必须至少包含一位数字才执行**。
本题的实现里，`P<CR>`、`W<CR>` 这类被直接丢弃。

**留给下次的判据**
> 任何“外部输入”都要假设它会收到垃圾。**未接的输入不是“没有信号”，而是“随机信号”**。
> 解析器的最小校验成本很低，收益是消灭一整类“参数自己变”的幽灵问题。

## 9. 自动轮换与手动选择抢控制权

**触发条件**
系统有一个“自动模式”（如每 2 秒自动换一种波形），同时又有手动选择按键，
而手动选择没有强制退出自动模式。

**现象**
按一下键，波形变了，但很快又变回去；按住不放反而“稳定”在某一种。

**为什么难发现**
看起来像“按键接触不良”或“连发太快”。实际是两套逻辑在写同一个寄存器，
谁后写谁生效。

**修复**
1. 上电默认**关闭**自动模式（本项目默认固定正弦）。
2. **任何**手动操作都强制 `auto = 0`。
3. 自动模式只能由显式命令开启（如串口 `W4`）。

**留给下次的判据**
> 同一份状态只允许一个“主人”。只要有自动逻辑，就一定要回答：
> **手动介入时，自动逻辑怎么退出？** 这一条没想清楚，就会出现“按键不听话”。

## 10. 每周期点数非整数，示波器读数缓慢抖动

**触发条件**
DDS 输出频率与 DAC 更新率之比不是整数（几乎总是如此）。

**现象**
示波器的 Vpp 和频率读数在小范围内周期性跳动，波形看起来在“呼吸”。
幅度抖动约 ±1.6%。

**为什么难发现**
第一反应是“系统不稳定”或“电源纹波”。实际是完全确定的数学结果。

**定量解释**（本项目 20 kHz）
```
采样率 347,222 SPS ÷ 输出频率 20,000.1 Hz = 17.36 点/周期   ← 非整数
采样点偏离峰顶最大 0.5/17.36×360° ≈ 10.4°
幅度误差 1 − cos(10.4°) ≈ 1.63%
拍频 347222 − 17×20000.1 ≈ 7.2 kHz → 每 139 µs 重复一次
```

**判别方法**
把频率设成 1 kHz（每周期 347 点）。**若抖动完全消失，就是采样比问题；**
若 1 kHz 下 Vpp 仍在跳，才需要去查基准电压或电源纹波。

**缓解**
- 提高采样率（受接口速率限制）；
- 输出加低通重构滤波器（把承载抖动的镜像压掉）；
- 示波器开 Average。

**留给下次的判据**
> 高频段出现的“不稳定”，先算一下**每周期点数**再动手。
> 点数 < 20 时，你看到的抖动基本都是采样造成的，不是电路问题。

## 11. 零阶保持台阶被当成 bug

**触发条件**
DDS + DAC 结构，输出频率接近采样率的 1/20。

**现象**
正弦波是阶梯状，20 kHz 时一个周期只有十几个台阶。

**为什么难发现**
低频（1 kHz）时完全光滑，只有高频才出现，容易怀疑“高频路径有问题”。

**定量判断**
每周期点数 = 采样率 / 输出频率。本项目采样率 347 kSPS：

| 输出 | 点数 | 观感 |
|---|---|---|
| 1 kHz | 347 | 光滑 |
| 10 kHz | 35 | 细看有台阶 |
| 20 kHz | 17 | 明显阶梯 |

DAC 在相邻采样点之间**保持**前一个值，这就是零阶保持。它不补点。

**修复**
只有两条路：
1. 提高采样率（受 SCLK 上限约束，本项目从 195 kSPS 提到 347 kSPS 已接近上限）；
2. 加**二阶**低通重构滤波器。

> 一阶 RC 不够。本项目实测：一阶（1 kΩ+2.2 nF，fc=72 kHz）对 327 kHz 镜像只有 −13 dB，
> 肉眼几乎看不出改善；二阶 Sallen-Key（fc=45 kHz）可达 −34 dB，叠加零阶保持本身的
> −24 dB 后残余约 −58 dB，台阶消失。**别用一阶去试，会得出“滤波没用”的错误结论。**

**留给下次的判据**
> 判断“台阶是不是 bug”：算点数。点数够（>100）还有台阶 → 查代码；
> 点数不够（<20）→ 这是物理必然，只能从模拟侧解决。

## 12. 拿悬空引脚做复位

**触发条件**
板卡没有复位按键，为了“有个复位”，随手挑一个看起来空闲的引脚当复位输入。

**现象**
系统随机复位、偶发死机，或上电后有时能跑有时不能。

**为什么难发现**
“随机”是最难查的特征。而且复位引脚通常被认为是“不起眼的小事”。

**定位步骤**
1. 查这个引脚在原理图上接到哪里。如果是 NC（未连接），它就是一个天线。
2. 用示波器看该引脚：应该看到随机的窄脉冲。

**修复**
改用**纯上电复位**：上电后计数约 8 ms 再释放复位，不依赖任何外部引脚。

```verilog
reg [23:0] por_cnt;
reg        rst_n;
always @(posedge clk) begin
    if (por_cnt < 24'hFF_FFFF) begin
        por_cnt <= por_cnt + 1'b1;
        rst_n   <= 1'b0;
    end else begin
        rst_n   <= 1'b1;
    end
end
```

**留给下次的判据**
> **未连接的输入引脚等于随机信号源**，不能当复位、不能当使能、不能当模式选择。
> 板卡没有复位键，就用上电复位——这是标准做法，不是妥协。

## 附：这 12 条的共同规律

回头看，12 条里有 7 条（1、2、7、8、12 及 4、6 的一部分）本质是同一件事：
**“未定义的输入”被当成了“确定的信号”**。

- 悬空的按键 → 被当成有确定电平
- 错误的引脚表 → 被当成确定映射
- 悬空的 RX → 被当成没有数据
- 悬空的复位脚 → 被当成“没按下”
- 中文路径 / 错误编码 → 被当成合法字符串

所以最省时间的做法不是逐条背，而是养成一个习惯：

> **每引入一个外部输入，先问一句“如果它现在是悬空的/错的，我会看到什么？”**
> 然后把这个“什么”变成可观测量（一个串口字段、一个 LED、一行日志）。

本项目最后之所以能把 4 个现象一次定位，就是因为把按键原始电平做成了 `K=` 字段——
**把不可见的猜测变成了可见的数字**。
