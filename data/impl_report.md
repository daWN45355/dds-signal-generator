### 2.2 细节

**Slice 分布**：占用 392 个 Slice（4400 个中的 8.91%），其中 SLICEL 254、SLICEM 138。
LUT-FF 配对 305 对，完全利用的 70 对。唯一控制集 39 个 —— 这个数字偏大，
原因是各模块的复位与使能信号彼此独立，没有做控制集合并。对本设计规模而言，
39 个控制集远未造成布局压力，故未优化。

**LUT 输出使用**：778 个 LUT 只用 O6 输出，225 个同时用 O5 与 O6，0 个只用 O5。
说明综合器较好地复用了 LUT 的两个输出。

**寄存器类型**：631 个带时钟使能与同步复位，46 个带时钟使能与同步置位，
0 个异步复位/置位。这与源码风格一致 —— 全设计采用同步复位，
避免异步复位释放时的亚稳态风险。这条在 `report/impl_1/` 的 "Summary of Registers by Type" 表里可直接看到。

**主要原语**：FDRE 631、LUT2 380、LUT6 294，其余为 LUT3/LUT4/LUT5 与 CARRY4。

### 2.3 解读

资源占用远低于器件容量，这是"全并行、无缓存"设计风格的结果：
系统中没有任何数据 FIFO 或帧缓存，正弦表只用 1024×12 位，因此 BRAM 几乎未动。

这个余量有明确的工程意义：后续若要做任意波形（AWG），
把正弦表换成双端口 BRAM 并扩容到 4096 点，BRAM 占用也只是从 1 个块涨到 2 个块，
LUT 侧几乎不变。6 个 DSP 中也可以再塞进一级插值滤波器。资源不是瓶颈。

## 3 时序收敛

数据源：`impl_1/dds_key_top_timing_summary_routed.rpt`。

### 3.1 时钟定义

| 时钟 | 波形 (ns) | 周期 (ns) | 频率 (MHz) | 来源 |
|---|---|---|---|---|
| `sys_clk` | {0.000 10.000} | 20.000 | 50.000 | 板载 50 MHz 有源晶振，引脚 N18 |

约束语句：`create_clock -period 20.000 -name sys_clk [get_ports clk]`

全设计单时钟域，无跨时钟域路径（Inter Clock Table 为空），无 MMCM/PLL（Clock Management 全为 0）。
这一点是有意为之：单时钟域意味着不存在跨域握手问题，也就没有相应的亚稳态风险需要论证。

### 3.2 时序结论

| 指标 | 数值 | 含义 |
|---|---|---|
| **WNS**（最差建立裕量） | **+3.089 ns** | 关键路径延迟 16.911 ns，余量 15.4% 周期 |
| **TNS**（总建立违例） | **0.000 ns** | 0 个失败端点 / 共 1643 个 |
| **WHS**（最差保持裕量） | **+0.121 ns** | 保持时间同样满足 |
| **THS**（总保持违例） | **0.000 ns** | 0 个失败端点 / 共 1643 个 |
| WPWS（最差脉宽裕量） | +9.500 ns | 0 个失败端点 / 共 680 个 |
| 分析端点总数 | 1643 | 寄存器到寄存器、输入输出路径 |
| 最大路径延迟 | 6.546 ns | 其中逻辑 3.978 ns（60.8%）、布线 2.568 ns（39.2%） |

**建立时间、保持时间、脉宽三类检查全部零违例**，且多角落分析（Slow/Fast 双角）均通过。

### 3.3 关键路径分析

报告给出的最差路径：

```
Slack (MET) : 3.089ns
  Source:       u_drv/din_reg/C          （sys_clk 上升沿触发）
  Destination:  dac_din                  （输出端口，受 set_output_delay 约束）
  Requirement:  20.000ns
  Data Path:    6.546ns  (logic 3.978ns 60.773% / route 2.568ns 39.227%)
  Logic Levels: 1  (OBUF=1)
```

这条路径值得说明：**它不是内部寄存器到寄存器的路径，而是寄存器到输出端口的路径**，
逻辑级数只有 1（一个 OBUF）。之所以成为最差路径，是因为约束里写了
`set_output_delay -clock sys_clk 5.000 [get_ports {dac_din dac_sclk dac_cs}]`，
把 5 ns 的外部建立时间预留给了下游（DAC 的 SCLK 建立要求）。

推论：**内部寄存器间路径的余量比 3.089 ns 更大**，即 WNS 是被 IO 约束"顶"出来的，
不是被逻辑深度顶出来的。因此"最高 59 MHz"（由 1/(20−3.089) 反推）是一个**保守下界**；
若把 IO 约束放宽，实际可跑频率更高。本设计用不到，如实说明而不夸大。

### 3.4 一次时序不收敛的历史

这一版 WNS 为 +3.089 ns，但首次实现时是 **−1.877 ns**，时序不收敛。

原因是频率换算用了除法器：`freq_word = freq × 2³² / 50_000_000`，
综合器生成一个 64 位除法器，组合路径深达 30 余级，50 MHz 下无法满足。
功能仿真完全正确，所以"仿真过了但板上波形乱"—— 这类问题在仿真里永远抓不到。

修改方式：利用 2³² / 50 000 000 ≈ 85.89934592，而 `f × 85.89934592 = (f × 1441151881) >> 24`，
把除法换成常数乘法加右移。1441151881 = round(85.89934592 × 2²⁴)，
相对误差 6×10⁻¹⁰，对 20000 Hz 而言绝对误差 1.2×10⁻⁵ Hz，完全可忽略。
改完 WNS 从 −1.877 ns 变为 +3.089 ns，关键路径缩短 4.966 ns。

结论写进踩坑清单第 3 条：**在 FPGA 里"可综合"不等于"可实现"，除法和取模应尽量转成乘加与移位。**

## 4 功耗

数据源：`impl_1/dds_key_top_power_routed.rpt`，Design State: routed。

| 指标 | 数值 |
|---|---|
| 片上总功耗 | **0.097 W** |
| 　动态功耗 | 0.004 W |
| 　静态功耗（器件漏电） | 0.093 W |
| 结温 Tj | 26.1 °C |
| 最高允许环境温度 | 83.9 °C |
| 有效 θJA | 11.5 °C/W |
| 估算置信度 | **Low** |

按部件拆分：时钟网络 0.002 W，Slice Logic <0.001 W，其余（BRAM、DSP、IO）均 <0.001 W。

**必须说明的三点**：

1. 置信度为 **Low**，因为未提供仿真活动文件（SAIF/VCD），Vivado 只能按默认翻转率估算。
2. 这是**工具估算值，不是实测值**。本设计未做功耗实测。
3. 该数值只覆盖 PL 部分，**不含** DAC（TLV5618A 双通道）、基准源（REF3030）、
   扩展板与核心板的电源转换损耗。因此本文不声称"整机功耗"这一指标。

静态功耗占 93% 是 28 nm 小规模设计的正常现象：器件漏电是常数项，
而本设计动态翻转的节点只有 1003 个 LUT 与 677 个触发器，几乎可以忽略。
这也意味着降功耗在本设计上没有优化空间 —— 除非换更小的器件。

## 5 DRC、方法论检查与布线

### 5.1 DRC

`impl_1/dds_key_top_drc_routed.rpt`：**17 条违规，全部为 Warning，0 条 Error**。

| 规则 | 级别 | 说明 | 数量 |
|---|---|---|---|
| DPIP-1 | Warning | DSP 输入未加流水寄存器 | 6 |
| DPOP-1 | Warning | DSP PREG 输出未加流水 | 5 |
| DPOP-2 | Warning | DSP MREG 输出未加流水 | 5 |
| ZPS7-1 | Warning | 使用了 Zynq 器件但未例化 PS7 | 1 |

前三条都是"给 DSP 加流水级可以跑更快"的建议。本设计 WNS 有 3 ns 余量，
加流水级会增加延迟、改变时序关系（幅度乘法结果要与 SPI 帧对齐），收益为负，故不采纳。

`ZPS7-1` 是纯 PL 设计在 Zynq 器件上的必然提示，不影响功能。

### 5.2 方法论检查（Methodology DRC）

这一次实现的方法论检查共 5 条 Warning（该报告未复制进本包，见第 8 节说明）：

| 规则 | 说明 | 数量 |
|---|---|---|
| TIMING-18 | `heart` 端口缺少 output delay 约束 | 1 |
| XDCH-2 | `dac_cs` 等 4 个端口 min/max 延迟相同 | 4 |

- `heart` 是 1 Hz 心跳灯，人眼观察用，不需要时序约束，缺 output delay 是合理的。
- `XDCH-2` 提示 `set_output_delay` 同时被当作 min 和 max 使用。对 SPI 这类
  单向、无双向握手的接口，min=max 正是设计意图，不是错误。

这两类警告都已在约束文件中以注释说明理由，未做"为消除警告而改约束"的处理。

## 7 与基线比对的方法

`checks/check_impl.py` 做的是"回归判据"这件事：
把新生成的报告解析成数值，与 `baseline.json` 里记录的本次结果比较，
判断改动是否引入了性能退化。

判据：

| 指标 | 阈值 | 理由 |
|---|---|---|
| WNS 下降 | ≤ 0.30 ns | 换机器、换 Vivado 补丁版本的正常浮动范围 |
| 单项资源上涨 | ≤ 2.0 个百分点 | 同上，综合器启发式的正常波动 |

输出示例（本包实测）：

```
> python checks\check_impl.py --proj report
==========================================================
实现结果: impl_1\dds_key_top_timing_summary_routed.rpt
==========================================================
  WNS +3.089 ns    TNS 0.000 ns
  WHS +0.121 ns    THS 0.000 ns
  关键路径 16.911 ns（按 20 ns 约束估算最高约 59.1 MHz）
----------------------------------------------------------
  LUT      1003 / 17600    5.70 %  Δ+0.00pp
  FF        677 / 35200    1.92 %  Δ+0.00pp
  BRAM        1 / 60       1.67 %  Δ+0.00pp
  DSP         6 / 80       7.50 %  Δ+0.00pp
  IOB        11 / 100     11.00 %  Δ+0.00pp
==========================================================
[PASS] 与基线一致（时序未回退、资源未超容差）
```

这段输出是本包实测结果，与第 2、3 节表格里的数字逐项一致 ——
也就是说报告里写的数字不是抄来的，是脚本从原始报告里读出来并打印的。

这个脚本不依赖本项目任何符号，改三个变量即可用于别的工程，已作为技能包的一部分提交。
