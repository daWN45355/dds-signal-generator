# 提示词工作流

四条经过本项目验证的提示词模板。它们解决的是**用大模型做工程判断时最容易失真的四个场景**：
架构推导、报告解读、外设核对、故障归因。

每条都写明：什么时候用、怎么用、模板原文、以及本项目里它实际产出了什么。
**模板里的 `{}` 是占位符，替换成自己的内容。**

---

## 通用约定（先读这段，能省一半返工）

1. **永远给出“可观测的量”**，不要给感受。
   ✗ “波形不对” → ✓ “示波器 CH1 频率显示 20.00 kHz，峰峰值在 4.6~4.9 V 之间跳变，周期约 0.5 s”
2. **要求模型列出“如果这个结论错，会看到什么”**。这一句能挡掉大部分一本正经的胡说。
3. **要求区分“已确认 / 推测 / 需实测”**。工程问题上三者混淆是最大的坑。
4. **一次只问一个决策点**。把“该用哪块板、该用哪个 DAC、该怎么接按键”塞进一句话，得到的回答通常都很空。

---

## 模板 1：从算法描述推导软硬件划分

### 适用场景
拿到一个题目（“做个信号发生器 / 图像处理 / 电机控制”），还不确定哪些部分该放 PL、
哪些放 PS、哪些根本不该用 FPGA 做。

### 模板原文

```
我在用 FPGA 做一个 {题目}，目标指标是 {列出 3~5 条硬指标，如频率范围、精度、吞吐}。

硬件条件是：{器件型号与资源，如 XC7Z010：17600 LUT / 60 BRAM / 80 DSP}，
主时钟 {50 MHz}，可用外设 {串行 DAC xxx、UART、按键}。

请按下面格式回答，不要写背景介绍：

1. 把系统拆成数据流，逐步列出每一步的“运算类型 / 位宽 / 速率（Hz）/ 是否可流水化”。
2. 对每一步判断：必须 PL / 建议 PL / 必须 PS / 两者皆可，并用一句话说明理由。
3. 指出哪一步是整个系统真正的瓶颈（决定最高性能的那一步），并给出量化依据。
4. 列出至少两个“看起来该用 FPGA、其实不该”的环节，说明原因。
5. 最后给出：如果资源只剩 20%，你会砍掉哪些功能，按顺序。

要求：所有速率和位宽都用具体数字，不要出现“较高”“足够快”这类描述。
```

### 使用说明
- 第 1 步产出的数据流表，直接可以拿去当报告“系统方案”一节的素材。
- 第 3 步是本模板的核心。**多数人会把瓶颈判断错**：以为瓶颈在算法，
  实际往往在“接口速率”或“存储带宽”。
- 第 4 步用来防止过度设计。

### 本项目已验证结果
用这套模板分析 DDS 时，第 3 步给出的瓶颈判断是：
**“瓶颈不在相位累加器（50 MHz 下一拍完成），而在 DAC 的串行帧长”**。
据此算出采样率上限 347 kSPS，与后来实现的状态机逐拍计数完全一致
（一帧 71 时钟 × 2 帧 + 帧间 2 ≈ 144 时钟 @50 MHz）。
这个结论直接决定了“20 kHz 只有 17 个点”这一后续所有讨论 ——
如果在方案阶段没有算出来，就会在联调时误以为是程序 bug。

## 模板 2：根据综合报告定位瓶颈

### 适用场景
综合或实现跑完，WNS 为负、或资源超限、或明明逻辑很简单却占用异常高。

### 模板原文

```
下面是 Vivado 的实现结果摘要，请帮我定位问题并给出改法。

【器件】{xc7z010clg400-1}
【时钟约束】{create_clock -period 20.000 -name sys_clk [get_ports clk]}
【时序摘要】
{WNS / TNS / WHS / THS 四个数与失败端点数}
【关键路径前 5 条】（直接粘贴报告里的 Source / Destination / Path Group / Delay 五行表）
【资源】{LUT / FF / BRAM / DSP / IOB 的 Used 与 Util%}

请回答：
1. 关键路径的延迟主要花在“逻辑级数”还是“布线”上？依据是哪几个数。
2. 这条路径对应的 RTL 大概是哪类操作（比较器 / 乘法 / 除法 / 大位宽选择 / 跨模块组合路径）？
3. 给出 2~3 个具体改法，按“改动量从小到大”排序，说明每个改法预计能省多少 ns 以及为什么。
4. 如果改法需要在“增加一拍延迟”和“增加资源”之间取舍，你选哪个，为什么。
5. 明确指出：仅凭这份报告**无法判断**的部分是什么。

不要建议“加流水线”这种笼统说法，要具体到改哪一行表达式。
```

### 使用说明
- **别把整份报告贴进去**。只贴“汇总表 + 关键路径前 5 条”，信息密度最高。
- 第 5 问很关键：它会告诉你还需要补什么信息（通常是具体 RTL 片段），避免在信息不足时得到错的结论。

### 本项目已验证结果
本项目第一次实现 WNS = **−1.877 ns**。用这套模板分析后，指向的结论是
“一条 32 位除法路径”。实际 RTL 里正是：

```verilog
freq_word = f * 85899 / 1000;      // 除法器，组合延迟过大
```

改成常数乘法 + 移位：

```verilog
wire [45:0] fw_prod = freq_hz[14:0] * 46'd1441151881;   // ×85.89934592×2^24
freq_word <= fw_prod[45:24];                            // 右移 24 位
```

WNS 由 **−1.877 ns 提升到 +3.089 ns**，关键路径缩短 4.97 ns，功能不变
（定点误差 6×10⁻¹⁰）。这一步是整份报告里“时序收敛”一节的实证来源。

> 经验：在 FPGA 里，**除法和取模几乎总该换掉**。换成乘常数加移位，
> 或者干脆改成累加式（每次加固定步长）。这一条能解决入门项目里大部分时序违例。

## 模板 3：外设引脚与电平核对

### 适用场景
板卡资料零散、社区帖子互相矛盾、丝印与原理图对不上。典型症状是“按了键没反应”“读到的电平一直是高”。

### 模板原文

```
我有一块 {板卡型号}，需要确认 {外设名称，如 4 个按键} 的真实引脚与电平极性。

我掌握的资料是（只列你确实有的，没有就写“无”）：
- 原理图页码/文件名：{...}
- 我读到的网络标号与引脚：{逐个列出，格式：网络名 → 引脚号}
- 社区资料声称：{...}
- 实测现象：{例如“上电后参数自己往低走”}

请按下面格式回答：
1. 先判断：我给的这批信息里，哪些是“观测事实”、哪些是“二手结论”。分开列。
2. 给出一个能在 10 分钟内做完的**实测方案**，用来一次性确定引脚映射和极性。
   方案必须满足：只用 {万用表 / 串口打印 / 示波器} 之一，不需要拆焊。
3. 给出“实测结果 → 结论”的对照表：看到什么读数，就说明什么。
4. 列出如果我按社区资料接线，最可能出现的 3 个具体现象。
5. 指出这个方案在什么情况下会失效（例如引脚被复用、有串联电阻、上下拉被内部配置覆盖）。

不要直接告诉我引脚应该是什么，除非你能说明依据来自哪份资料的哪一页。
```

### 使用说明
- 第 2 问是这个模板的价值所在：它逼模型给出**可执行的自检方案**，而不是给结论。
- 第 5 问能提前发现“内部上下拉与外部上下拉打架”这类隐蔽问题。

### 本项目已验证结果
本项目的按键曾被社区资料误导为 `T19 / P19 / U20 / U19 / V20`，
实际那五个网络是 VGA_G2 / VGA_B4 / VGA_HSYNC / VGA_G3 / VGA_VSYNC，属于视频接口。
按该模板给出的方案，我们把四路按键的**原始电平**放进状态报文实测，得到：

| 操作 | 原始电平 | 按下状态 |
|---|---|---|
| 不按 | 1111 | 0000 |
| KEY_1 (G19) | 1110 | 1000 |
| KEY_2 (J19) | 1101 | 0100 |
| KEY_3 (K19) | 1011 | 0010 |
| KEY_4 (L16) | 0111 | 0001 |

结论一次定案：**引脚映射正确，按键低有效**。在此之前基于“空闲读高就是悬空”的推断
导致了完全相反的处理，详见 `04_pitfalls/` 第 1 条。

## 模板 4：多现象故障归因

### 适用场景
一次出现好几个看似无关的异常，每个都去单独查会浪费大量时间。
**这类问题的正确做法是先找“能同时解释全部现象的那个假设”。**

### 模板原文

```
我的系统出现以下 {N} 个异常，同时发生：

{逐个列出，每条都要有可观测的数字或读数，不要写“不正常”}
1. ...
2. ...
3. ...

已知条件（可能相关的）：
- 我改过的地方：{...}
- 我确定没问题的：{...}（并说明是怎么确认的）
- 目前能观测的量：{串口回传 / 示波器 / 万用表 / 打印日志}

请回答：
1. 列出能**同时解释全部 N 个现象**的假设，最多 3 个，按可能性排序。
   如果某个假设只能解释其中 1 个现象，标注“部分解释”。
2. 对每个假设，给出一个“一次性区分”的观测：做这一个动作，看一个读数，就能排除或确认。
   要求这个动作不拆硬件、不改代码超过 10 行。
3. 指出这些现象中最不可能是同一个原因的那一个，并说明理由。
4. 最后给出排查顺序：先做哪一步，为什么先做它。
```

### 使用说明
- 关键在于“同时解释全部现象”。单个现象的解释通常有很多种，能一次解释全部的往往只有一个。
- 第 3 问防止“为了统一而强行统一”，避免把无关问题硬凑成一个原因。

### 本项目已验证结果
本项目的四个现象：① 参数自己往低走；② 相位一直转；③ 方向自动变成“减”；
④ 真按住某个键反而没反应。

按本模板回答给出的核心假设是：**“空闲状态被当成了'四个键都按住'”**。
它一次解释了全部四个现象：空闲被当成按住 → 四路连发 → 频率每 50 ms 减、
相位每 50 ms 加、方向被翻一次；而真按下时该路信号反向，反而停住。

验证只需一个动作：看状态报文的 `K=` 在空闲时是 0000 还是 1111。
结果为空闲 1111、按下 1110，立刻确认 —— 从提出假设到修复不到 20 分钟。
在此之前，逐个现象排查花了一整天。

> 这个模板的通用形式是：**当 N 个异常同时出现时，优先怀疑“它们共享的那一个输入是错的”**，
> 而不是去修 N 个地方。
